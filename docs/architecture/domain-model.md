# CarryLink domain model and lifecycle

2026-09-08 · **Proposed** · Original CarryLink synthesis from the [benchmark](../research/open-source-benchmark.md). All policy-sensitive transitions/thresholds require [H1–H5 approval](architecture.md#human-decision-gates). No production SQL or implementation is supplied.

## Entity definitions

Ownership below distinguishes the participant controlling data from the service authorized to mutate it. All persistent records have opaque ID, creation/update timestamps and version where mutable. Use stable geographic IDs, UTC instants with original time zone, integer physical units and explicit currency/minor units; never floating-point money. Avoid hard deletion of active commitments.

| Entity / purpose and ownership | Important fields / relationships | Lifecycle and invariants |
| --- | --- | --- |
| **User**: authenticated person; identity service, user edits permitted profile fields | auth issuer/subject unique pair, display name, locale, account status; one person may have both capability profiles | ACTIVE/SUSPENDED/CLOSED; verified email does not imply KYC. Participant cannot self-assign operator roles. Account closure preserves unresolved obligations under approved retention. |
| **Traveler**: user's carrying capability; user profile, trust service eligibility | unique userId, capability status, public bio; many Trips; verification and payout account references | DRAFT/ELIGIBLE/RESTRICTED; optional separate one-to-one profile, no separate login. Eligibility is policy-derived, not a badge Boolean. |
| **Sender**: user's sending capability; user/request service | unique userId, capability status, contact preference; many Requests | ACTIVE/RESTRICTED; thin optional one-to-one profile; ordinary User suffices until sender-specific fields exist. Sender may also be Traveler on another transaction. |
| **Trip**: traveler's offered journey, trips service | travelerId, origin/destination city, handover/arrival windows, zones, status, terms version; Flight segments, Capacity and many Orders | DRAFT → PUBLISHED ↔ PAUSED → IN_PROGRESS → COMPLETED; pre-travel CANCELLED/EXPIRED. Cannot silently edit contracted route/time or reduce capacity below commitments. Same user cannot carry own request. |
| **Flight**: scheduled air segment within a Trip; traveler input, optional later verified source | tripId, sequence, airline/flight number, departure/arrival airport, scheduled/actual times, provenance | PLANNED/DELAYED/DEPARTED/ARRIVED/CANCELLED. Flight number alone is not unique: date and airports matter. A flight update never proves item delivery. Use owned TripFlight records initially rather than global airline database. |
| **Capacity**: Trip's offered carrying limits, trips service | unique tripId, total grams/cm³, max item dimensions; Reservation children | AVAILABLE/FULL derived, CLOSED when trip unavailable. Reservations plus committed load never exceed either bound. Luggage allowance is not equivalent to spare capacity. Dimensions need explicit fit policy, not volume alone. |
| **Request**: sender's transport need, requests service | senderId, route, readyAt/deadline, item description/category/version, grams/cm³/dimensions, declared value/currency, budget, photo keys, restricted recipient reference | DRAFT → OPEN → COMMITTED → FULFILLED; OPEN → WITHDRAWN/EXPIRED. One active commitment per request for MVP; material edits invalidate proposals and require renewed review. No split parcels initially. |
| **Match**: saved proposal between one Request and Trip, matching service and participant consent | requestId/tripId and their versions, quote/ranking version, proposer, each consent timestamp, expiry, reason breakdown | PROPOSED → ACCEPTED/REJECTED/WITHDRAWN/EXPIRED; STALE on changed inputs. Search candidates need not be rows. Acceptance requires both parties' current consent and atomic revalidation; one match creates at most one Order. |
| **Order**: binding transport agreement, order service | requestId/matchId/tripId, sender/traveler, immutable item/route/contact-minimized terms snapshot, fee policy/amount/currency, consent, physical status, version | Main flow below; one Order per accepted Match. Snapshot changes require explicit amendment/reconsent or cancellation/rebooking; profile edits cannot rewrite history. |
| **Payment**: collection attempt, payment service/provider authority | orderId, provider/account/reference, idempotency key, amount/currency, captured/refunded amounts | CREATED/PENDING/AUTHORIZED/CAPTURED/FAILED/CANCELLED/UNKNOWN. Multiple attempts permitted, one active collection obligation; total valid captures cannot exceed approved amount. Browser redirect is not capture proof. |
| **Payout**: traveler settlement obligation and attempts, finance service/provider | orderId, payee account, entitlement amount/currency, hold reasons, transfer reference, bank payout reference, attempt keys | HELD/ELIGIBLE/PROCESSING/TRANSFERRED/PAID/FAILED/REVERSED/UNKNOWN. PAID means confirmed bank payout if observable; otherwise explicitly report transfer only. Never duplicate settlement or pay funds owed as refund. |
| **Message**: durable participant communication, messaging service | conversationId/orderId, authorId, body, sequence, client message key, moderation metadata | SENT/REDACTED; unique conversation/author/client key; only members send/read. Plain text, bounded size; no fabricated online/read status. System events distinguished from user messages. |
| **Review**: completed transaction feedback, author with moderation service | orderId, authorId, subjectId, rating, text, publication status | PENDING/PUBLISHED/HIDDEN; one per author/subject/order, only actual counterparty; no self-review. Rating scale/publication timing need H5; aggregates exclude ineligible records. |
| **Dispute**: service complaint and resolution case, participant opens, authorized operator resolves | orderId, issue type, evidence keys, owner, deadlines, resolution, approval, linked refund/hold | OPEN → INVESTIGATING → RESOLVED → CLOSED; reopening per approved policy. At most one active service case per order; provider chargebacks are separately linked events. Resolution does not itself execute a refund. |
| **Handover**: origin transfer into traveler custody, custody service | orderId, planned place/window, sender/traveler confirmations, evidence, actualAt, attempt | PLANNED/PENDING/CONFIRMED/FAILED/CONTESTED. Confirmed only with approved two-party proof; token single-use and bound to order/participants. Payment and policy checks precede custody. |
| **Delivery**: destination receipt, custody service | orderId, recipient reference, planned/actual place/window, receipt evidence, attempts, delay reason | PENDING/IN_TRANSIT/READY/DELAYED/DELIVERED/FAILED/CONTESTED. Arrival at airport is not receipt. Recipient may differ from sender; use approved recipient challenge or operator-reviewed evidence. |
| **RiskFlag**: actionable concern, trust service/operator | subject (validated typed reference), category, severity, policy version, reason, evidence, reviewer | OPEN/REVIEWING/CLEARED/CONFIRMED. Unknown policy cannot produce automatic clearance. Flag is not a customs classification or identity result. |
| **IdentityVerification**: verification attempt, identity adapter/provider | userId, provider/reference, purpose, status, verifiedAt/expiresAt, minimized outcome, policy version | NOT_STARTED/PENDING/VERIFIED/FAILED/EXPIRED/REVOKED. Multiple attempts/history; provider verification only changed by authenticated evidence/reconciliation. No client-supplied VERIFIED. |
| **AuditLog**: accountability, append-only service writer | actor/type, action, target, time, correlation, reason, minimal before/after metadata | Append; corrections reference previous record. No participant mutation; access and retention controlled. Exclude secrets and document bodies. |

Supporting records are necessary rather than hidden JSON: **Reservation** (HELD/COMMITTED/RELEASED/EXPIRED, request/trip/order, units, expiry); **Refund** (REQUESTED/PROCESSING/SUCCEEDED/FAILED/UNKNOWN, payment, approved amount/reason); **PayoutAccount** (provider eligibility and bank reference); **Conversation/Membership**; **OrderEvent**; **Outbox/Job**; **ProviderEvent**; **LedgerEntry**; **AdminGrant**. Provider transfer/bank-payout attempts can become separate tables beneath Payout. Route is an origin/destination value object referencing City/Airport lookup entities, not a fleet route-planning subsystem. Audit and ledger history have different access and retention purposes.

Cardinality: User 1→many Trips/Requests; Trip 1→many Flight segments, 1→1 Capacity; Request many↔many Trip via Match; accepted Match 1→0..1 Order; Order many→1 Trip, 1→many payment/refund attempts/messages/custody attempts; at most one active Request commitment. Constraint/transaction design must enforce these, not just TypeScript types.

## Boundaries that must remain distinct

- **Trip vs Flight:** the former is a person's commercial offer and handover plan, the latter an air segment. Shared aircraft does not imply shared ownership or capacity.
- **Trip vs Capacity:** capacity is reservable inventory with concurrent updates; descriptive trip editing must not overwrite reservations. One capacity aggregate per trip is enough initially.
- **Request vs Order:** editable need versus consented historical agreement. Withdrawal before agreement is different from cancellation after commitment.
- **Match vs Order:** suggestion/negotiation versus contract. Searching creates no obligation; accepting stale candidates must fail safely.
- **Payment vs Payout:** money collected from sender versus money sent to traveler; timings, eligibility, failure and reversal differ.
- **Handover vs Delivery:** origin custody proof versus destination receipt proof, often involving a different person.
- **RiskFlag vs IdentityVerification:** item/behavior/transaction concerns versus identity evidence. Neither substitutes for the other.

## Order state machine

Use a physical/contract lifecycle plus independent financial/case state, not one overloaded status column. The requested labels below form a UI projection; every label is accounted for. `CREATED` is an internal event emitted during accepted-match order creation; `MATCHED` is its initial persisted state in that transaction. Do not persist unbound shell orders for every search.

| Allowed transition | Authorized trigger | Required evidence/guard and effect |
| --- | --- | --- |
| CREATED → MATCHED | Order service handling final participant consent | Current consent from both, eligible route/items/users, accepted Match, atomic exclusive Request and capacity hold; immutable quote/terms snapshot |
| MATCHED → PAYMENT_PENDING | Sender checkout command; payment service | Valid unexpired hold, server-priced contract, unique payment attempt; persist effect intent before PSP call |
| PAYMENT_PENDING → PAID | Verified provider event/reconciliation | Exact amount/currency/order binding and captured funds; atomically convert unexpired hold to commitment |
| PAID → HANDOVER_PENDING | Order service | Persisted successful capture, agreed origin arrangement, current eligibility; event transition may occur immediately but is recorded |
| HANDOVER_PENDING → HANDED_OVER | Custody service after participant proof | Sender and traveler confirmations/approved evidence, no unresolved blocking case, actual timestamp |
| HANDED_OVER → IN_TRANSIT | Traveler command | Confirmed origin custody and recorded departure evidence; no future fabricated timestamp |
| IN_TRANSIT → DELIVERY_PENDING | Traveler command | Arrival/readiness evidence and recipient arrangement; airport arrival alone may establish readiness, not delivery |
| DELIVERY_PENDING → DELIVERED | Recipient confirmation or authorized evidence review | Approved recipient challenge or reviewed receipt evidence, actual timestamp |
| DELIVERED → COMPLETED | Order service/operator under approved policy | Confirmation/window policy satisfied, no open case or blocking risk; release eligibility evaluated separately, never immediate blind payout |

### Exceptions and recovery

| Label / transition | Authority and evidence | Recovery and invalid shortcuts |
| --- | --- | --- |
| PAYMENT_PENDING → PAYMENT_FAILED (financial projection) | Provider definitive failure | Retry → PAYMENT_PENDING with new attempt only while hold valid; physical state remains MATCHED. Unknown timeout is pending reconciliation, not failure. |
| MATCHED/PAYMENT_PENDING/PAYMENT_FAILED → EXPIRED | Expiry worker using DB time | Release hold and request commitment atomically. Never expire confirmed custody or a captured order via this path. |
| MATCHED through HANDOVER_PENDING → CANCELLED | Authorized participant request adjudicated by approved cancellation policy/operator | Stop new payment/custody actions, resolve provider uncertainty, release unused capacity once; captured payment creates refund review. No automatic post-handover cancellation. |
| IN_TRANSIT/DELIVERY_PENDING → DELIVERY_DELAYED (Delivery overlay) | Traveler or deadline worker with evidence/reason | Preserve physical state; revised estimate/resolved incident clears delay overlay. Delay does not prove refund entitlement or change capture status. |
| PAID through COMPLETED → DISPUTED (case overlay) | Participant within approved window, or operator/provider incident | Preserve custody and prior physical state; hold unsettled remuneration. Already paid funds create recovery case, not fictionally reversed money. Resolution clears overlay, resumes recorded physical state or records exception closure. |
| Captured Payment → REFUND_PENDING (refund overlay) | Finance command after authorized decision | Amount bounded by captured less successful/pending refunds; hold conflicting payout. Failure stays unresolved/retryable with reason. |
| REFUND_PENDING → REFUNDED | Provider-confirmed full refund | Partial success is PARTIALLY_REFUNDED, not full REFUNDED. Physical history remains; no resurrection of cancelled order. |

Post-custody loss, refusal, trip cancellation or return requires an operator case and **CLOSED_EXCEPTION** terminal outcome after custody/disposition and financial resolution are recorded. It must not be represented as COMPLETED delivery. Item return uses a new custody event/return arrangement; it never deletes original handover. These additional states avoid forcing exceptions into a false success path.

Late payment after hold expiry/cancellation: record capture truth; do not revive Order or steal capacity from another order. Open reconciliation/refund case, freeze payout and follow approved remedy. Race between payment confirmation and expiry is serialized against the same reservation/order rows. Release after cancellation frees capacity only if the parcel never entered custody; consumed journey capacity is not made sellable by refund.

Invalid transitions include MATCHED → HANDED_OVER, AUTHORIZED → PAID without capture, IN_TRANSIT → COMPLETED, client → PAID/REFUNDED, cancelled/expired → active, arbitrary status reversal, delivery → automatic payment success and COMPLETED → payout despite hold. Reject with conflict and retain an audit trace. Repeated command/evidence IDs return prior result; stale aggregate versions require reload. UI displays custody, payment and case status together so a dispute does not hide where the item is.

Tests must cover every allowed edge and denied actor, stale/duplicate commands, two simultaneous match acceptances, dimension/weight capacity limits, expiry/capture races, two-party receipt evidence, delayed receipt, post-completion dispute and partial/full refund reconciliation. Approval of the transition table and evidence policy is required before production implementation.

## MVP matching

Candidate discovery is read-only. Hard filters run before ranking: active traveler/Trip, distinct sender/traveler, directed CN→DE or DE→CN route enabled by policy; exact city or approved airport-to-city mapping; request ready before handover, arrival plus approved delivery buffer no later than deadline; available weight and volume and item dimension fit; approved item category/risk status; budget/quote currency compatibility. Unknown measurements, missing policy or stale eligibility exclude booking and return an explanation/review requirement. Exact cities initially avoid unsupported radius promises; no geocoding or route optimization needed.

Time comparisons use instants and origin/destination zones, including German daylight-saving boundaries. Search `date` currently lacks semantics: label future fields as pickup-ready/departure window and destination deadline; do not silently equate them. Capacity shown in search is advisory and rechecked transactionally at acceptance.

Prefer deterministic **lexicographic scoring** initially: exact compatible route first, larger nonnegative delivery slack next, approved total price ascending next, eligible completed-order reputation next, stable Trip ID final tie-break. Route is already a hard filter; airport/city preference only ranks genuinely approved alternatives. New travelers have neutral unknown reputation, not fabricated zero reliability. Founder may change this ordering before implementation. Return versioned reasons and values, not a percentage probability. Never let reputation compensate for an ineligible item or insufficient capacity.

Store Match only when a participant proposes a commitment. Record input versions and accepted quote, not a permanent row for every candidate pair. Query indexes cover route/status/departure and active requests; optimize with measured plans. Emit privacy-minimized candidate→proposal→acceptance→completion metrics. Future evolution: tune rule order with observed outcomes; introduce explainable weighted scoring after offline evaluation and fairness review; add geospatial support only for proven city coverage needs; ML only with sufficient outcome data, measurable uplift and unchanged hard safety/eligibility gates.
