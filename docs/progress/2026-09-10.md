# Frontend interaction sprint

## Task goal
Implementation Engineer; completed as a frontend-only prototype on `feature/frontend-interactions`. User authorization: 2026-09-10 frontend interaction sprint request. Acceptance: navigable EN/ZH/DE mock traveler/trip and sender/request journeys through deterministic matching and order confirmation; responsive and accessible; typecheck, lint, build and browser checks.

## Implementation summary
Inspection found only `/`, functional dependent selects and language switching, static percentage matches, and preview-only traveler/account actions. Added focused App Router pages while retaining the existing homepage, logo, tokens, cards, navigation and native dialog.

- Navigation and CTAs connect Home, homepage How It Works/Safety sections, dashboard, trips, requests, matches and orders. Language context now spans routes. Mobile menu retains outside-click/Escape behavior.
- Homepage search navigates with validated shareable URL values. Candidates reflect exact directed cities, departure date and available mock weight/volume. Empty results are explicit. Removed fixed scores and percentage bars.
- Traveler dashboard supports create, three form steps, previous/edit/review, validation, publish feedback, pause/resume, editing and matching sample sender requests. Saved trips also appear in homepage listings.
- Sender journey collects route, deadline, item, approximate weight/volume/dimensions and coarse delivery area, validates, reviews and saves locally. Drafts survive internal navigation.
- Matches show deterministic reasons, expandable details, date/capacity sorting and order-review links. Request matching compares arrival with deadline and excludes self-matches and requests already used by a demo order.
- Order review displays traveler/trip, item/route and unquoted pricing. An explicit demo acknowledgment enables confirmation. Saved order snapshots are reviewable in dashboard; trip editing/pause is disabled when a demo order uses it. This is a frontend consistency guard, not a production contract lifecycle.
- Root React context centralizes temporary records and drafts. Reload resets everything; missing record IDs show recovery links. No database, APIs, authentication, messaging, payment, KYC, dependencies or infrastructure added.
- Removed displayed unconditional verification, escrow, earnings/delivery statistics and protection claims in EN/ZH/DE. Profiles and marketplace are explicitly sample/demo data.

### Product, matching and architecture assessment

- **Journey coverage:** both Home→Traveler→Create Trip→Publish→Match→Order and Home→Sender→Create Request→Match→Order pass with ordinary inputs. Trip Previous/review/edit/pause/resume, retained sender draft across internal navigation, order acknowledgment gating, saved summaries and reload/missing-ID recovery work. Submitted-request editing is absent (R4); pause/resume is trip-only; withdrawal/cancellation is absent rather than falsely implemented. - **Coherence:** meaningful progress beyond disconnected screens: shared trips/requests/orders, real links, snapshots, both roles in one session. Remaining non-blocking naming issues include a sender returning to **Traveler dashboard**, **View Trip** opening a request form, **View all trips** opening a default-filtered match list, and mixed Trip/Reise and sender terminology in translated copy. Clarify these in a focused content pass.
- **Matching honesty:** no displayed Match Score percentages or probability bars found. `searchTrips` uses published status, exact directed cities, departure on/after date, and sufficient weight/volume. `compatible` adds different users and arrival on/before request deadline. Results use deterministic departure/ID order or capacity descending with stable tie-breaks. The shared reason sentence correctly summarizes those mock comparisons, but supplies no per-rule numeric breakdown; “dates fit” hides the different search/deadline predicates. **Best match** means first under the selected sort, not an independently evaluated quality. Traveler-side sorting compares the same trip for every request and therefore provides little useful distinction. Prefer explicit sort-relative labels and input/value explanations; H5 still governs live ranking.
- **State boundary:** authoritative mutable demo arrays and keyed drafts are centralized in root context; sample cards feed mock fixtures without another mutable store. Immutable order snapshots intentionally duplicate record values. Search draft and form step state remain local; draft keys include raw query strings, so alternate entry URLs can yield distinct drafts. Providers expose raw setters, and creation/guard logic remains in UI handlers: workable for this small demo, but not a drop-in backend service contract. Unused users/profile exports, old `Trip.price` fields and dormant preview/copy paths remain cleanup debt.
- **Capacity limit:** orders do not reserve/decrement trip capacity; later requests can reuse the original capacity. This is explicitly excluded by ADR-002 and is not a newly demanded production booking feature. Before broader prototype testing, make clear that capacity comparison ignores previous demo orders or agree a separately scoped simulation. Dashboard trip locks are local consistency guards, not a complete inventory model.
- **Routes/Next:** sensible App Router routes, `Link` and `router.push/replace`, awaited dynamic route params, Suspense around search hooks. No SPA page switcher, API routes, server actions, auth/provider/database code or dependency additions found. Root client providers alone are acceptable; R3 is the specific excessive rendering boundary. No production architecture proposal was accepted by this review.
- **Claims/pricing:** current reachable flows honestly say local demo, reload reset, no booking/payment, fictional profiles and unquoted prices. No traveler contact, identity verification, protection or delivery completion is asserted. Sample ratings remain illustrative; new “Demo” trips display rating 0 rather than an unknown reputation label. Dormant translations and unused trip-dialog rendering still contain legacy prices/payment text; these were not reachable in the reviewed flows and are debt, not evidence of a live payment feature.
- **Validation/error/loading:** native required/positive measurements and route/date ordering checks work on exercised paths. Generic form error marks all rendered input fields invalid, while route selects lack corresponding field-level error linkage; improve precision/accessibility. No backend network-failure/retry state exists because there is no service.
